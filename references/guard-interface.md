# Local guard v1: bounded interface

The executable is `scripts/toolkit_guard.py`; run `--help` for the five commands listed in `toolkit-safety.md`. JSON Schema lives at `references/workflow-contract.schema.json`. Keep both resources and all four guard/artifact helper modules together when packaging. Install the pinned validation dependencies in an isolated environment. Input files are strict JSON (duplicate keys and nonfinite constants fail). Structural unknown fields/versions fail closed; the CLI adds digest, path, provenance, arithmetic and review checks. A schema-valid file alone does not pass those checks.

All checks are read-only except new snapshots and new artifact receipts. No edits, rollback, approval creation, workflow-state persistence, issuance, or external actions occur. The supervised caller persists state/evidence and immutable prior revisions outside distributable sources. STDOUT is a JSON result; failures exit nonzero (`needs_human` on STDERR, or readback classifications on STDOUT). Save readback results beside the plan using a new local file. A `validated` state is not `final_verified`.

## Canonical digests and human confirmation

`H(x)` is SHA256 of UTF-8 `json.dumps(x, sort_keys=True, separators=(',', ':'), ensure_ascii=False, allow_nan=False)`; file/image digests hash exact bytes instead. Approval records have exactly `reviewer`, `purpose`, `digest`. The named human must actually confirm the displayed material. These editable records are audit aids, **not authenticated signatures or access controls**. The helper never creates them.

- Change approval: purpose `local_update`, digest `H(plan without approval)`.
- Scope approval: purpose `scope`, digest `H({project_id, revision, scope_digest, sources})` with those exact keys/values from state.
- Pricing approval: purpose `pricing`, same object plus `pricing_digest`.
- Estimate preparation approval: purpose `estimate_final`, digest `H(state without approvals and status)`. This binds the display name, revision, scope, price evidence, artifacts and their declared semantics, stage, next action, exceptions and other supported context. It is not artifact semantic verification.

Reindexing a changed drawing/quote invalidates old scope/pricing approvals even if the scope description did not change. Modifying displayed project context invalidates estimate preparation approval. Do not update digest/approval fields as a substitute for renewed human review.

## Change plans and recovery

Use `kind: change_plan`, integer `schema_version: 2`, nonempty operation ID, absolute target `root`, human-facing `selected_sections` labels, targets, and approval. Each target must bind a nonempty `section` label exactly matching an entry in `selected_sections` (no normalization or inferred mapping). For example, select `Company identity`, bind the target with `section: "Company identity"`, and select `selected_fields: ["company_name"]`. Labels do not authorize arbitrary fields: `selected_fields` is a separate exact top-level mapping-key allowlist. Each target also has a relative `path`, `format` (`json`, `yaml`, `markdown`, or `text`), complete UTF-8 string `before`/`after`, their hashes, and ordered `{before, after, count: 1}` contexts. For a newly absent target only, both before fields are null and the creation context is the empty string to the complete new image.

**Deprecated v1 compatibility:** `schema_version: 1` change plans retain the original field-key allowlist semantics: every target `selected_fields` entry must also appear literally in plan `selected_sections`; targets cannot contain `section`. Never reinterpret a v1 label as a field mapping or silently upgrade an approved plan. Migrating to v2 changes the approved digest and requires renewed human confirmation. The version, selected labels, target bindings, fields, and images remain covered by `H(plan without approval)`. Only change plans support v2; workflow states, pricing evidence, and receipts remain v1.

This adapter supports whole JSON/YAML mappings and Markdown with YAML frontmatter, using top-level selected fields. Markdown body bytes are represented by reserved field `__body__`: they must remain identical unless that exact field is explicitly selected in target `selected_fields`. In v2 the target also binds a selected human-facing section label; in deprecated v1 `__body__` must additionally appear in plan `selected_sections`. Plain references without frontmatter use `text` with only selected field `__body__`, with the same version-specific section binding. Exact unique contexts still bind every body edit; text mode makes no structured-field claims. Nested field selectors, binary changes, deletion, YAML custom types and ambiguous bulk replacements are unsupported; stop for separately reviewed support rather than invent fields. Unselected parsed fields must retain their exact JSON type and value. Each replacement context must occur exactly once. Repeated old strings elsewhere are preserved. New or malformed double-brace tokens fail. Existing tokens may remain during a partial staged update; repository source validation still requires registered contexts and release validation rejects required unresolved tokens. Staged contents travel in the plan itself; protect this confidential local file.

`check-change --plan P --root R` requires approved current before-images and writable targets/parents. `snapshot --plan P --checkpoint-dir C` requires a **new** directory with an existing parent, outside the target root and outside package inputs. Paths must be absolute where applicable; all symlink components and traversal are rejected. The helper checks capacity, writes/fsyncs/verifies numbered before-image files and an absent-state manifest, marks backups read-only, and never replaces an existing checkpoint. A partial checkpoint remains for human inspection, not automatic reuse. User-owned files remain editable by their owner: this is overwrite resistance, not tamper-proof storage. Concurrent hostile directory swaps are outside this supervised filesystem model.

Immediately before supervised edits, rerun `check-change`. `verify-change --plan P --checkpoint-dir C` verifies the saved manifest/backup hashes and classifies every target `before`, `approved-after`, or `conflict`. Only all approved-after returns `verified`; interrupted/conflicting/missing backup runs require a human. No automatic edit retries or restoration occur.

## Project state and pricing evidence

The schema enumerates required fields. `kind: workflow_state` has exact project root/identity, revision string, stage (`ROM`, `conceptual`, `formal`), status, domain, source index, scope, hashes, phases, approvals, artifact index, exception owners, and next safe action. Scope currently supports only `{description: nonempty text}`. Put detailed project entities, dates, intended use, assumptions and unsupported domain evidence in retained indexed local documents; never claim this bounded schema inferred or checked their contents.

Sources are local relative paths under root, each with exact project ID, content SHA256, revision/date/locator (nullable), and a nonempty missing reason whenever metadata is null. Remote URLs are not fetched: retain/index a reviewed local source copy. `scope_digest = H(scope)`; `pricing_digest = H(entire pricing_evidence)`.

Before pricing, an empty price/line index with zero totals is valid only while pricing is pending; no invented rates are required. Preserve actual takeoff quantities in an indexed, hashed local artifact.

Four ordered phases are `scope`, `takeoff`, `pricing`, `artifact`, each `{status, reason}`. The helper selects the first pending phase, or `human_review` if none; state `next_safe_action` must agree. Completed scope/pricing require matching approvals. Only ROM permits explicitly reasoned `not_applicable`; formal cannot silently inherit skips. Changed sources/artifacts or stale approvals stop resume; the tool never rewrites the state to hide an invalidation.

Pricing evidence separately indexes quantity evidence (source, unit, A–D rating) and price evidence (source type, source pointer, unit/currency, market, base rate, locality/escalation, adjustment basis, confidence, override/reason, estimator disposition/reviewer). Types are `quote`, `historical`, `published`, `assumption`; only explicit assumptions may have a null source pointer. Each line has a stable ID, division, quantity/unit, rate, amount/currency, separate evidence references, literal derivation `quantity * rate`, and visible allowance boolean.

Numbers are nonnegative Decimal strings. V1 supports only rate = base × locality × escalation rounded to cents (or explicit override); line = quantity × rate rounded to cents; division/subtotal sums; fee = subtotal × markup rate rounded to cents; total = subtotal + fee. Rounding is explicitly `ROUND_HALF_UP`, quantum `0.01`, markup basis `subtotal`. Mixed units/currencies, other conversions, negative credits, arbitrary formulas, multi-fee/retainage/prior-period models are **unsupported and block reconciliation**, not guessed. Formal prices require reviewed estimator disposition, and assumptions remain visible allowances. This verifies provenance links and arithmetic, not market accuracy.

## Consequential limits and artifact receipts

`approved_for_final` is accepted only for estimates with completed scope/takeoff/pricing, current scope/pricing/estimate_final approvals and no exceptions. Legal, safety and billing finalization adapters are not implemented, so contract/incident-report/sub-pay-app cannot promote past draft/review here. `final_verified` always blocks: visual/domain review adapters are unavailable. This is intentional bounded coverage, not a successful professional review.

`verify-artifact --artifact A --expectations E --receipt R` delegates to `artifact_checks.verify_artifact`; its module documents the expectations structure. R must be a safe, nonexistent absolute path with an existing parent. The CLI writes exclusively, fsyncs and reopens the receipt. It never overwrites an artifact/receipt or follows a destination symlink. Receipts retain actual file/semantic digests, checks, inspection gaps and `not_issued`. They are not approval or final status. Unsupported PDFs/formulas remain blocked by the artifact adapter.
